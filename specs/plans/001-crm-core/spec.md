# 功能規格：CRM 客戶關係管理系統核心

**功能分支**: `001-crm-core`

**建立日期**: 2026-03-30

**狀態**: 草稿

**輸入**: 使用者描述：「我想從零建立一個 CRM 系統：\n- 業務可以建立與管理客戶及公司資料。\n- 業務可以記錄每次聯絡內容與下一步行動。\n- 業務可以建立銷售機會，並設定階段、預估金額與預計成交日。\n- 業務主管可以查看銷售管線，以及每筆銷售機會的負責人與目前階段。\n- 只有具備權限的成員可以查看或修改客戶與銷售資料。\n- 系統需要包含可操作的網頁介面與後端 API。」

## 使用者情境與測試 *(必填)*

### 使用者故事 1 - 客戶與公司資料建立與管理 (Priority: P1)

作為業務人員，我希望能夠建立與維護公司資料及相關客戶聯絡人資訊，以便在一個地方集中管理所有客戶輪廓與聯絡方式。

**為何為此優先級**: 客戶與公司是 CRM 系統所有業務活動的基礎實體；若無法建立公司與客戶資料，後續的聯絡紀錄、銷售機會與銷售管線皆無法依附。

**獨立驗證方式**: 建立公司與客戶聯絡人，確認資料正確儲存、關聯建立，並能在列表與詳細頁面查詢與編輯更新。

**驗收情境**:

1. **Given** 業務人員具備資料維護權限，**When** 輸入有效的公司名稱、統一編號（選填）、產業類別並儲存，**Then** 系統成功建立公司資料並賦予唯一識別碼。
2. **Given** 系統中已存在「水球軟體」公司，**When** 業務人員為該公司新增客戶聯絡人「王大明」（包含姓名、電子郵件、電話、職稱），**Then** 系統成功建立客戶資料並關聯至「水球軟體」。
3. **Given** 系統中已存在客戶「王大明」，**When** 業務人員更新其職稱與聯絡電話，**Then** 系統更新該客戶資料並保留最新變更結果。
4. **Given** 未具備客戶管理權限的訪客或非授權使用者，**When** 嘗試建立或修改公司與客戶資料，**Then** 系統拒絕該操作並提示無權限。

**功能需求（FR）**:

- **FR-001**: 系統 MUST 允許具權限的使用者建立、檢視、編輯公司資料（包含公司名稱、統編/代碼、產業、地址）。
- **FR-002**: 系統 MUST 允許具權限的使用者在特定公司下建立、檢視、編輯多個客戶聯絡人資料（包含姓名、電子郵件、電話、職稱）。
- **FR-003**: 系統 MUST 在建立公司或客戶聯絡人時驗證必填欄位（公司名稱、聯絡人姓名、電子郵件），且電子郵件格式必須符合標準規範。
- **FR-004**: 系統 MUST 支援公司與客戶聯絡人資料的關聯查詢，能從公司檢視所屬聯絡人清單，亦能從聯絡人辨識其所屬公司。

**非功能需求（NFR）**:

- **NFR-001**: 公司與客戶聯絡人清單在單頁 50 筆記錄內，前端頁面渲染與 API 查詢回應時間 95% 須於 1 秒內完成。

### 使用者故事 2 - 記錄客戶聯絡歷程與下一步行動 (Priority: P2)

作為業務人員，我希望在每次與客戶通話、拜訪或會議後，能記錄聯絡內容、聯絡時間與下一步行動，以利持續追蹤客戶進度並防止重要跟進事項遺漏。

**為何為此優先級**: 建立客戶資料後，業務的核心價值在於持續互動與關係推進；聯絡歷史與下一步行動是銷售機會評估與客戶維繫不可或缺的動態依據。

**獨立驗證方式**: 針對指定客戶新增聯絡紀錄與下一步行動，確認時間軸正確呈現歷史歷程，且下一步行動能清楚被檢視與更新。

**驗收情境**:

1. **Given** 系統中存在客戶「王大明」，**When** 業務人員新增聯絡紀錄（聯絡方式為「電話」、內容為「需求訪談完成」、聯絡時間為當前時間，下一步行動設定為「9月5日提供正式提案」），**Then** 系統成功儲存該筆聯絡紀錄並將其關聯至該客戶。
2. **Given** 客戶已有歷次聯絡紀錄，**When** 業務人員進入該客戶歷程頁面，**Then** 系統依聯絡時間倒序（最新在上）顯示完整聯絡歷程。
3. **Given** 聯絡紀錄已設定下一步行動，**When** 業務人員檢視客戶資料，**Then** 系統明確顯示最近一筆待執行的下一步行動與預計日期。

**功能需求（FR）**:

- **FR-005**: 系統 MUST 允許具權限的業務人員為指定客戶建立聯絡紀錄，記錄聯絡方式（電話/會議/Email）、聯絡時間、內容摘要。
- **FR-006**: 系統 MUST 允許業務人員在聯絡紀錄中設定或更新「下一步行動」（包含行動內容與預計執行日期）。
- **FR-007**: 系統 MUST 依時間倒序呈現特定客戶的所有歷史聯絡歷程，且歷史紀錄建立後不得被任意刪改以保持跟進歷程的真實性。

### 使用者故事 3 - 銷售機會建立與階段推進 (Priority: P3)

作為業務人員，我希望針對有潛力的客戶建立銷售機會，設定階段、預估金額與預計成交日，並在每次商務進展時推進階段，以便掌握潛在營收與交易進度。

**為何為此優先級**: 銷售機會是 CRM 連接「客戶關係」與「業績成交」的核心轉換物件；明確的銷售階段與金額能將商機轉化為可衡量的商業價值。

**獨立驗證方式**: 建立銷售機會、綁定客戶與公司、更新各銷售階段（潛在 -> 已聯繫 -> 提案中 -> 已成交/已失敗），驗證階段移轉與金額更新。

**驗收情境**:

1. **Given** 系統已定義銷售階段（1.潛在、2.已聯繫、3.提案中、4.已成交、5.已失敗），**When** 業務人員「Alice」為「水球軟體」的客戶「王大明」建立銷售機會（名稱「企業版授權合約」、階段「潛在」、預估金額 300000 元、預計成交日為「2026-05-30」），**Then** 系統成功建立銷售機會並將負責人設為「Alice」。
2. **Given** 「Alice」負責的銷售機會目前處於「已聯繫」階段，**When** 「Alice」完成需求訪談並將階段推進至「提案中」，**Then** 系統更新該銷售機會階段為「提案中」，並記錄階段變更時間點。
3. **Given** 「Alice」負責的銷售機會，**When** 非負責人且非主管的成員「Bob」嘗試修改該銷售機會之階段或預估金額，**Then** 系統拒絕該操作並維持原狀。

**功能需求（FR）**:

- **FR-008**: 系統 MUST 支援標準銷售機會階段：潛在（Prospecting）、已聯繫（Contacted）、提案中（Proposal）、已成交（Closed Won）、已失敗（Closed Lost）。
- **FR-009**: 系統 MUST 允許業務人員建立銷售機會，包含機會名稱、關聯客戶與公司、負責業務、目前階段、預估金額（正數數值）、預計成交日。
- **FR-010**: 系統 MUST 允許銷售機會負責人或業務主管更新銷售機會之階段、預估金額與預計成交日。
- **FR-011**: 系統 MUST 限制只有負責業務本人或業務主管才能推進該筆銷售機會的階段。

**非功能需求（NFR）**:

- **NFR-002**: 銷售機會金額計算與儲存必須精確到小數點後兩位（或整數貨幣單位），不得因浮點數運算產生數值誤差。

### 使用者故事 4 - 業務主管銷售管線綜覽 (Priority: P4)

作為業務主管，我希望能夠查看全團隊的銷售管線（Pipeline），一覽每筆銷售機會的負責人、目前所處階段與預估金額分佈，以便進行業績預測與團隊資源調配。

**為何為此優先級**: 在個別業務能記錄客戶與銷售機會後，管理階層需要綜觀全局以進行決策與指導；管線綜覽能將分散的機會聚合為管理價值。

**獨立驗證方式**: 以業務主管角色登入，檢視銷售管線看板或分階段摘要，驗證所有業務負責的機會依階段分欄呈現，並正確統計各階段總金額與筆數。

**驗收情境**:

1. **Given** 團隊已有多筆分別由不同業務負責且處於不同階段的銷售機會，**When** 業務主管查看銷售管線，**Then** 系統以階段分組（Kanban 檢視或分組清單）顯示所有銷售機會，標示每筆之名稱、負責人、預估金額與關聯公司。
2. **Given** 業務主管查看銷售管線，**When** 檢視各階段統計，**Then** 系統顯示各階段的機會筆數與加總預估金額。
3. **Given** 一般業務人員登入系統，**When** 進入銷售管線頁面，**Then** 系統預設展示該業務負責之銷售機會範圍，防止未授權存取其他業務敏感業績資訊。

**功能需求（FR）**:

- **FR-012**: 系統 MUST 提供銷售管線（Pipeline）綜覽視圖，依銷售階段分類展示進行中與已結束的銷售機會。
- **FR-013**: 系統 MUST 在管線視圖中展示每筆機會之關鍵資訊（負責人、公司名稱、金額、目前階段、預計成交日）。
- **FR-014**: 系統 MUST 提供各銷售階段之匯總指標（階段機會總筆數、階段預估總金額）。
- **FR-015**: 系統 MUST 允許業務主管依負責人、日期區間進行管線篩選。

---

### 邊界情況

- 當建立銷售機會時輸入負數金額或無效日期，系統 MUST 拒絕儲存並提示有效輸入範圍。
- 當銷售機會已進入「已成交」或「已失敗」之結案狀態，系統 MUST 提示並要求確認是否允許重新開啟或再次變更階段。
- 當公司底下仍有關聯客戶或進行中的銷售機會時，系統 MUST 禁止直接刪除該公司，並提示需先解除或移轉關聯。
- 當使用者連線工作階段逾期或未通過身份驗證時，系統 MUST 拒絕任何資料寫入操作並提示重新登入。
- 當多名使用者同時檢視銷售管線時，系統須確保資料讀取的一致性與快照正確性。

## 需求 *(必填)*

> 各使用者故事的專屬 FR / NFR 已直接列在故事底下；本節只保留無法合理歸屬單一使用者故事，或明確跨越多個使用者故事的全域需求。

### 全域需求

#### 功能需求

- **FR-016**: 系統 MUST 實作角色型存取控制（RBAC），區分「業務主管（Sales Manager）」與「一般業務（Sales Rep）」角色，只有具備對應權限之成員可查看或修改指定範疇之客戶與銷售資料。 [NEEDS CLARIFICATION: 一般業務是否開放跨人員檢視客戶基本聯絡簿，或僅限負責業務查看，暫定預設為可檢視基本資料、僅負責人可編輯修改]
- **FR-017**: 系統 MUST 提供可操作之現代化網頁介面（Web UI）與完整對應之 RESTful 後端 API。
- **FR-018**: 所有後端 API 必須具備身份驗證與授權防護，未攜帶有效憑證之請求 MUST 被拒絕（HTTP 401/403）。

#### 非功能需求

- **NFR-003**: 系統網頁介面必須在標準桌上型電腦瀏覽器（Chrome, Firefox, Safari, Edge 最新版本）上排版正常，並符合直覺操作之 UI/UX 標準。
- **NFR-004**: 系統錯誤回應必須採用標準結構化格式（包含錯誤碼、友善錯誤提示），且不得向前端外露資料庫內部堆疊或敏感技術資訊。

### 關鍵實體 *(若功能涉及資料，必填)*

- **公司 (Company)**: 商業組織實體，包含公司名稱、統編/代碼、產業類別、聯絡地址與建立時間，為多個客戶聯絡人的母體。
- **客戶聯絡人 (Contact)**: 隸屬於特定公司的個人客戶，包含姓名、電子郵件、電話、職稱與所屬公司關聯。
- **聯絡紀錄 (Interaction)**: 與客戶的互動歷程紀錄，包含聯絡方式（電話/會議/Email）、聯絡時間、內容摘要與下一步行動指派。
- **銷售機會 (Opportunity)**: 針對特定公司或客戶之潛在交易，包含機會名稱、負責業務、目前階段、預估金額、預計成交日與建立時間。
- **銷售階段 (Sales Stage)**: 銷售機會推進之標準狀態流程，包含「潛在」、「已聯繫」、「提案中」、「已成交」、「已失敗」。
- **使用者與角色 (User & Role)**: 系統操作人員與所屬角色（業務主管、一般業務人員），界定其資料可視範圍與管理權限。

## 成功標準 *(必填)*

### 可量測成果

- **SC-001**: 具備權限之使用者能在 1 分鐘內完成一家新公司與一位客戶聯絡人的建立與關聯。
- **SC-002**: 業務人員記錄一次聯絡歷程並設定下一步行動的操作時間能在 30 秒內完成。
- **SC-003**: 100% 建立之銷售機會均具備明確的負責業務、當前階段與預估金額，無孤立或未定義階段之商機。
- **SC-004**: 業務主管於銷售管線視圖中能 100% 精準掌握全團隊所有負責人、階段與加總預估金額。
- **SC-005**: 100% 未授權之 API 存取與跨權限修改請求皆被正確攔截與拒絕（0% 權限越權外洩）。

## 假設

- 系統初版幣別預設採用新台幣（TWD），不涉及多幣別動態匯率即時折算。
- 銷售機會階段流向以由前向後推進為典型路徑，但允許直接推進至結案階段（已成交/已失敗）。
- 系統初版預設提供內建之使用者帳號密碼與角色授權管理，暫不介接外部單一登入（SSO/LDAP）機制。
- 網頁介面以桌上型瀏覽器體驗為第一優先考量，初版不強制支援行動裝置原生 App。
